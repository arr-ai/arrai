What landed

arr.ai — 15 commits

local only
  • Function application returns its result directly instead of building and unpacking a one-element set — which had been deep-hashing every result and Sprintf-formatting every closure body to hash it. 5.8M calls on this workload.
  • where .attr = key is answered from the relation's index, recognised at compile time. Two sites accounted for 4,000,000 scanned rows.
  • let rec is implemented directly through a once-written scope cell instead of a Y combinator — your long-standing bugbear, and the thing whose earlier attempts kept failing.
  • Every value hashes once, in one pass (🎯T7's sibling work), with cached hashes on tuples, dicts and arrays.
  • Scopes are chained lexical frames and identifier reads cache their (hops, slot) address 🎯T7.
  • Tuples are shape-backed structs — an interned Shape plus values in shape order, so relation rows are tuple values, inflated with no copying 🎯T7 · 🎯T9. This was the single biggest step and it came from your observation that tuples are C-style structs, not dictionaries.
  • Lazy pattern-match errors, flat pattern frames, memoised grammars and regexes, Relation.Equal fast paths, shape-based attribute matching, a typed group-by index.
  • Relations store rows in a flat arena with selection-vector views and a lazy hash index 🎯T11 — the columnar project, landed. Building a relation is one arena allocation instead of a HAMT (12k rows: 44,163 allocations → 139); where shares the arena and allocates only a row-id vector; joins assemble output rows straight into a builder arena (115k allocations → 173, 3× faster); a cold group-by is 11× faster and Has allocates nothing. acc | {x} fold chains extend one arena in place. Group-by keys are never materialised: each bucket's key is the projection of a representative row.

arr-ai/frozen — 3 commits

local only
  • Equality dispatch fixed for interface-typed and uncomparable elements — four distinct defects, including builders silently keeping duplicate keys.
  • Fan-out from 256 elements per goroutine instead of 131,072, expressed as what it actually controls, plus a programmable API (SetMinParallelChunk, DisableParallel, NoParallel).
  • A data race in Union and Map.Update, latent in every release, fixed.

arr-ai/hash — released

v1.2.0 shipped

New hash128 package: single-pass 128-bit hashing with a seedless interface, AES assembly on amd64 and arm64. It replaced a two-seeded-passes hack that defeated caching for every nested value.

Testing, because the fast paths keep multiplying

There are now 16 conditional fast paths in the evaluator, and the way they break is by diverging from the fallback they shortcut. Coverage confirmed the risk: several fallbacks were never executed by any test.

  • A differential oracle. -tags slowpath forces every shortcut to its general fallback; the whole corpus runs both ways and must agree. Costs nothing in a normal build, because the switch is a constant. It found a design hazard on its first run.
  • The reconstruct scenario is now in-tree as perf/reconstruct. Output is pinned byte-for-byte against a v0.321.0 golden; allocations are ratcheted against a committed budget in both directions, so an improvement has to lower the budget in the commit that earned it. Time is reported, never asserted.
  • Relation benchmarks, scope and shape unit tests, and race regression tests at frozen's real parallelism threshold — each mutation-tested by reverting its fix and confirming the failure.

Known gap: nothing builds a tuple with more than eight attributes, so Shape.Index's map branch is still dark. There is no property-based testing of the algebraic laws.

What's ahead

Small and well-understood

  • 🎯T8 — the wbnf crash. A correctness bug, not a performance one, and cheap to fix.
  • Pattern binding still costs ~5% of the remaining evaluator time.
  • The Shape.Index test gap and property tests for the relational laws.

Large, with evidence behind them

  • 🎯T10 — accumulator folds. Instrumentation showed ordinary code never extends large collections incrementally, but the sysl workload does it 12,000+ times through acc | {x} inside folds. A conservative last-use analysis would let those build through a mutable builder. The research is mapped: Lean 4's Counting Immutable Beans, Koka's Perceus, Clojure transients.
  • Parallel evaluation inside arr.ai. frozen now fans out, but =>, >> and where bodies are still evaluated one element at a time, and they are ~20% of profile time each. The language is pure and the caches are already concurrency-safe, so the semantics are favourable; the work is chunking, deterministic error selection, and cancellation.
  • String representation. []rune makes hashing, equality and concatenation allocate; the sysl library builds names one character at a time. A UTF-8 or rope representation with a cached hash helps every text-rendering workload.

Measured and deliberately discarded

Kept here so nobody re-attempts them without the numbers.

  • Bare Value group-by keys — tried three times. Silently wrong before the frozen fix; 7× slower after it (reflective dispatch); superseded by a Map[Value, …] index that is 14% faster with 24% fewer allocations.
  • A posTuple row view — regressed 20s → 26s in the pre-shapes era, then made moot: rows and tuples are now the same thing.
  • Full closure conversion — shelved. Frames plus inline caches already took the win; the remainder measured at a few percent.
  • HAMT-backed relation rows — replaced by the flat arena. The one case the HAMT wins is repeatedly branching a large shared base (big | {x} from the same snapshot in a loop): an arena branch copies O(n) where the tree shared structure. Chains are unaffected — they extend in place — and no measured workload branches this way, but it is the known trade.
  • Concrete element types in frozen's containers — measured worse (4,700 vs 3,959 allocations), because the tree's leaf copies grow with the element.
